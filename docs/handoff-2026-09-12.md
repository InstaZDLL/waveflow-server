### Three states, and the trap the previous handoff named

`TrackMetadataPatch` now declares every field as `Option<Option<T>>` behind
`#[serde(default, deserialize_with = "present")]`. The outer `Option` is
presence and the inner one is the value, which is the only way serde can tell an
absent key from a `null` one.

Two things were learnt while wiring it:

- **An empty patch must write nothing.** `{}` was still taking the writer gate
  and emitting a `track`/`upsert`, so every client on the event feed refetched a
  track nobody had changed. The role check stays; the write does not happen.
- **A list correction cannot be previewed.** Artists and genres are
  materialised, so restoring them re-reads the file. The editor offers the
  restore without showing what it will produce, and says so.

### What the canvas needed that no document said

**Nothing on a track says it carries one.** `Song` has no canvas field, and
RFC-009 deliberately keeps the link off the track row. The web client therefore
asks by minting a ticket: `POST /tracks/{id}/canvas-ticket` answers 404 when
there is no canvas, which is the same answer it gives for a track the account
cannot see. `canvasUrl` reads a 404 as "none" and throws everything else — a
server that failed to answer must never be read as a track without a loop.

**`accepts_canvas` is its own door.** RFC-009 decision 5 split it from
`accepts_uploads` precisely so a read-only server can still take loops, and
neither flag was readable over the API before this session. Both are on
`GET /api/v2/libraries` now. Removal is *not* gated on the flag — closing a
library to loops must not strand the ones it holds — so the editor withholds the
picker and keeps the remove button.

### What the seek fix decided

A cache fill now runs behind a seek, at the lowest priority the server has: it
starts only after the live stream has its slots, takes a global slot only when
another stays free — two permits acquired at once and one handed straight back,
so no gap exists — and never counts against the account's own limit. It runs
**outside** the cache lock, because the play a seek abandons still holds that
lock for the moment it takes to notice its consumer left, and the seek lands
inside that moment. It is bounded by the track's length plus a minute, since a
fill has no listener whose departure could end it.

**A server with a single transcode slot never has one to spare**, so it keeps
the old behaviour. That is written in the API guide rather than left to be
discovered.

> **Verified 2026-09-12**, against the operator's own library rather than only
> in tests: the longest of its 164 tracks, six minutes forty, played from the
> top and dropped after two seconds — cache empty, a seeking range refused with
> `416`, which is the precondition that makes the rest mean anything. The seek
> that followed showed `active=2` on a server with four slots, the live stream
> and the fill beside it, and the next play answered `bytes=64-127` with `206`
> from a committed 4.8 MB file. The fill committed **about a second after the
> seek's stream ended**: the extra slot costs seconds, not the length of the
> track, which is the assumption the whole design rested on. Nothing under the
> library root was modified.

> [RFC-010](rfcs/RFC-010-external-scrobbling.md). It decides the hook point

> durable outbox drained by a seventh background task, submissions queued while
> "now playing" kept out of the request path entirely, credentials in two
> tiers — the provider's application keys at the deployment, the account's

> the first outbound HTTP this server would ever make. No code yet.
>
> **Revised the same day**, after an external review found it promising more
> than an outbox can give. A transactional outbox is atomic with our own queue
> and never with a third party, so the guarantee is exactly-once *enqueue*
> here and at most one attempt for an *ambiguous* outcome there: a response
> lost after the provider recorded the listen cannot be told from a request
> that never arrived. The queue also freezes an immutable envelope rather than
> re-reading the track, which bites harder here than the reviewer knew, since
> #186 lets a correction rewrite the title and the credits between the listen
> and the send.

## Traps

**A `cd` in one parallel shell call moves the other call's directory.** An
inversion script that began with `cp src/media.rs …` ran from `webapp/`, so the
copy failed, the chain stopped, and the suite that followed passed — a "proof"
with no defect ever reintroduced. Absolute paths in every inversion script, and
**print the inverted line in the log** before the test result. When an inversion
produces no failure, suspect the inversion first; the same lesson cost the
2026-09-10 session three times over.

**A catch-all mock answers routes it was never meant to.** The e2e suite's
`/api/v2/tracks/{id}` branch answered `/tracks/{id}/lyrics` with a track, and
`Lyrics` reads `value.structured_lyrics[0]`, so the playing page crashed the
moment a test first visited it. No test had, in four sessions of web work.
**A page with no end-to-end test has no mock either**, and the two absences hide
each other.

**Playwright runs against `webapp/dist`.** A source change that is not rebuilt
is tested in its previous form, and the failure looks like a bug in the new
code. `bun run build` before the suite, every time.

**React sets `muted` as a property, not an attribute.** `toHaveAttribute` finds
nothing; `toHaveJSProperty` is the assertion. The same holds for the other media
properties React writes this way.

**A review that cites a rule can still be citing the wrong one.** CodeRabbit
asked for tests "hermetic" enough not to spawn FFmpeg, quoting `AGENTS.md`'s
line about service containers — PostgreSQL and Better Auth — against a rule
`CLAUDE.md:35` states outright: *FFmpeg and ffprobe must be on `PATH`*. The same
misreading is recorded in `handoff-2026-09-06.md`. Its other finding on the same
PR was right and was fixed. **Verify each finding against the code and the
repository's own rules; neither the bot's confidence nor its quotation is
evidence.**

**Two adjacent flags are not one flag.** `accepts_uploads` and `accepts_canvas`
answer different questions, and a client that reads one for both hides a feature
in exactly the installation it was split for. `handoff-2026-08-30.md` wrote that
sentence about the server; it held again a session later, about the client.
