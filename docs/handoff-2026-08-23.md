## The mission from here

Written on 2026-08-23 in the order I would take them. Three of the four are
closed; what is left is §4, and the other three are what made it due.

### 1. Break up `src/` — done, PR #137

`src/api/` for the `/api/v2` surface, `src/subsonic/` for the façade,
`src/services/` split by domain across fourteen `impl DomainServices` blocks.
The largest file left in the tree is `catalog.rs` at 1 671 lines; nothing under
the three new directories exceeds 571. `http` was renamed `api`, because that is
the surface it serves.

Taken as pure movement and proved so: for each of the three files the sorted set
of non-blank content lines was compared before and after, and the whole
difference was scaffolding, visibility widened for items now called across a
boundary, and rustfmt rewrapping what those prefixes pushed past 100 columns.

**The one thing that proof could not see**, and the reason the warning above it
was right: the splitter recognised functions, types and `impl` blocks as
top-level items but not `mod`, so `http.rs`'s trailing `#[cfg(test)] mod tests`
was swallowed by the item above it and filed under `error.rs`, which covers
neither test. Content was preserved, so every check passed. Filing is what a
person has to check.

### 2. The named follow-ups

- **~~Give the track PID a job.~~** Done, PR #139. `track.pid` is the track spec
  evaluated over the file's tags, written on every apply and consulted as a third
  relocation step, after the path and the content hash. It stays a hint and never
  becomes an identity — track ids are still drawn at random — and it moves
  nothing unless exactly one candidate survives removing the tracks the walk
  found and the ones already claimed. The scanner's skip path backfills a missing
  hint, so an existing catalogue gets one from an ordinary scan rather than
  needing a full one.

  Two things the review caught that the first commit had wrong. A hint written
  under one spec was being compared against a lookup computed under another, and
  those are not separate namespaces: two specs evaluating to the same string
  would have handed a new file an unrelated track's favourites. A boot that finds
  the track spec changed now clears every stored hint before any scan uses the
  new rule — no rescan, since the backfill puts them straight back. The claim
  that a stale hint "costs a missed relocation, never a wrong one" was written
  into `CLAUDE.md` and the migration before it was true; both were corrected.

- **~~Artist favourite remapping.~~** Done, PR #140. It was worth the thirty
  lines. `reconcile_catalog_identity` remaps `user_star` and `user_rating`
  when `pid.artist` changed, **before** requesting the rescan — the only moment
  the old identifier and the name that produced it are both still on the
  `artist` row. Albums are not remapped and cannot be: their spec reads
  `albumversion` and `releasedate`, which live on the files.

  The review caught that moving the rows one at a time depends on the order they
  came back in — one artist's new identifier can be another's old one, and the
  first artist's favourite was then carried onto the second's row, or lost. Every
  pair is now computed first and moved in two phases through a namespace no
  identifier can occupy. No spec this engine can parse actually produces that
  chain, because only `albumartistid` carries a value for an artist; the test
  builds the rows by hand and says so, because the code cannot see that argument
  and a wider `PidSource` would make it reachable.

### 3. Album output fields — done, PR #140

All five. `originalReleaseDate`, `releaseDate`, `releaseTypes[]` and
`recordLabels[]` describe the release, so they sit on the album and fill the way
`year` does; `discTitles[]` holds one title per disc, so the tag lands on the
track and the album derives the list from its available tracks, grouped per disc
with `MIN`. `LABEL` first, `PUBLISHER` second. The three arrays are emitted empty
rather than absent — under both names an album is rendered by, `album` and, in a
directory, `child` — and the dates are omitted when unknown, as the reference
omits them. They are stored as the file spelled them and taken apart only at the
wire: `1998-11` is a year and a month, and a head that is not exactly four ASCII
digits is no date at all.

The same pull request closed the four findings deferred from #137: the N+1 reads
in `playlists_on` and `now_playing`, `search3` paging in memory rather than in
SQL, unbounded identifier lists on `star`/`unstar`/`scrobble`, and unbounded
playlists.

**The desktop asked for four things** and the arbitration was given on
2026-08-24.

| | What | State |
| --- | --- | --- |
| (a) | Cacheable artwork, and the `429` contract | Done, PR #143 |
| (b) | `PATCH /api/v2/tracks/{id}` — write a track's tags | Designed, not built |
| (c) | Accept an incoming file | Needs RFC-007 |
| (d) | A canvas asset per track | After (c) |

(a) shipped with a distinction worth carrying: artwork addressed **by hash** is
immutable, artwork addressed by a track, album or artist id is **not** — that
alias resolves whichever cover the entity carries now, and a rescan moves it.
Both send an `ETag`, so revalidating the alias costs a `304`. `public` was
refused on both: the route is tenant-checked and two libraries holding the same
cover share its hash.

**And a fifth item now precedes (b): the library event stream.** The server has
no such thing — the scanner writes nothing to the journal, and
`/api/v2/scans/{id}/events` is one job's progress, not a change feed. Every
projection of user state converges; nothing tells a client that a *track*
changed. (b), (c) and (d) all need it, and building it at (b) removes the
riskiest line of (b)'s own estimate — admitting a `track` type to `sync_event`
would have meant rebuilding that table around its `CHECK`.

Three things it has to get right, all established rather than assumed:

- **Its own sequence.** `sync_event.cursor` is a single global
  `AUTOINCREMENT`; sharing it would have a rescan advance the sequence every
  favourite cursor is measured against.
- **Revocation for free.** Filter the read on `library_member` at query time,
  as every other projection does, and losing access stops delivery on the next
  request with no revocation list to keep.
- **Retention from day one.** The user journal has no compaction at all
  (`src/sync.rs:271` says so), and a first scan of 50 000 tracks is 50 000
  events. The precedent to reuse is the one the user journal already has: answer
  "you are too far behind, take a snapshot".

One thing nobody had named, and the reason the stream matters beyond `PATCH`:
**an external retag moves a track's `full_hash` silently.** The design for (b)
never rewrites a file, so `PATCH` cannot stale the desktop's reconciliation
link — but an operator retagging with Picard does. The scan's skip condition
requires `existing.full_hash == input.full_hash`; different bytes fail it, the
apply runs, and the track keeps its id while its hash changes. Nothing tells the
desktop. The stream has to carry that as an event kind of its own.

## Traps this session paid for

**`DROP TABLE` and foreign keys.** SQLite runs an implicit `DELETE FROM` before
dropping a table. Children with `ON DELETE CASCADE` are emptied; a child with
`ON DELETE RESTRICT` raises a deferred counter that is never cleared, so the
commit fails while `PRAGMA foreign_key_check` reports nothing wrong. An empty
database migrates cleanly, which is why the whole suite stayed green. A
migration file cannot save itself — `PRAGMA foreign_keys` is a no-op inside a
transaction — so the runner suspends enforcement and answers for it with a
`foreign_key_check` afterwards.

**A test that models the fix instead of the thing.** The rebuild test shipped in
#126 built a toy two-table schema with no `RESTRICT` child. It proved the
technique and nothing about the migration. A migration test starts from a
populated catalogue at the previous schema version, or it proves nothing.

**Writing the right value in the documentation and deriving another in the
code.** This happened four times. The last one cost a failed release: the README
and the Compose file both said `ghcr.io/instazdll/…`, and the workflow was built
from `${{ github.repository }}`, which keeps the owner's casing. Before claiming
a behaviour exists, read it in the code or write the test that fails without it.

**A green pull request on a red base.** Dependabot merged the `rand` 0.8.7 →
0.10.2 bump (#133) at 05:02 on 2026-08-24, and `main` stopped compiling:
`rand::rngs::OsRng` and `rand::RngCore` no longer exist under those names, and
`src/security.rs` is the crate's only user of either. The module split merged on
top of it six hours later with its own CI green — its branch predated the bump
and was never rebased — and inherited the red without contributing to it. Fixed
in #138. **Check the CI colour of the base commit before merging, not only the
pull request's**, and when the diff of a red merge contains nothing that could
explain it, look at what landed on `main` since the fork point.

**Review counts do not trend.** Successive passes returned 14, 9, 10, 1, 1, then
10 findings — the last pass, on the final commit, found the most serious one of
the series. A falling count is not evidence of a settling surface.

## House rules that are not negotiable

Every code change goes through a branch and a reviewed pull request; only
documentation may go straight to `main`, and that authorization is asked for each
time. Commits are signed off (`git commit -s`) and follow Conventional Commits.
Migrations are immutable once merged. Audio files are never written. No tag or
release is created without an explicit request from the operator.
