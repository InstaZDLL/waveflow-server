## The mission from here

Nothing is blocking. In the order I would take them:

### 1. Break up `src/`

The one thing the operator asked for and did not get. Twenty-one files flat, and
three of them enormous:

| File | Lines |
| --- | ---: |
| `services.rs` | 4 273 — a single `impl DomainServices` of some 3 600 |
| `subsonic.rs` | 2 434 |
| `http.rs` | 2 415 |

The shape agreed on: `src/api/` for the `/api/v2` surface, `src/subsonic/` for
the façade, `src/services/` split by domain across several `impl DomainServices`
blocks — which Rust allows within one crate.

It was deliberately deferred until after the tag, so `v2.0.0-beta.0` would point
at the code the campaign actually exercised. That reason has expired. **Take it
as a pure-movement pull request** with no behaviour change: the compiler catches
a bad move, but not a method filed under the wrong module, so the diff has to
stay readable as movement.

### 2. The named follow-ups

- **Give the track PID a job.** The track spec is implemented and tested but
  governs nothing: track identifiers stay random because six tables cascade off
  them. `track.pid` as a relocation hint for a re-encoded file is the idea.
- **Artist favourite remapping**, if judged worth the thirty lines. The
  documentation currently states plainly that it does not exist, which is the
  honest position until it does.

### 3. Album output fields

`originalReleaseDate`, `releaseDate`, `releaseTypes[]`, `recordLabels[]`,
`discTitles[]` are still absent, and honestly declared so under the presence
rule. `ItemKey::Label` and `ItemKey::Publisher` exist in lofty, so
`recordLabels[]` is the cheap one.

### 4. Before a stable tag

Replay the clients again if the wire moves. The rule that has paid twice: **never
conclude from what the client shows when the server can be asked.** It
disqualified three "server defects" reported in good faith in one evening.

## Traps this session paid for

**`DROP TABLE` and foreign keys.** SQLite runs an implicit `DELETE FROM` before
dropping a table. Children with `ON DELETE CASCADE` are emptied; a child with
`ON DELETE RESTRICT` raises a deferred counter that is never cleared, so the
commit fails while `PRAGMA foreign_key_check` reports nothing wrong. An empty
database migrates cleanly, which is why the whole suite stayed green. A
migration file cannot save itself — `PRAGMA foreign_keys` is a no-op inside a
transaction — so the runner suspends enforcement and answers for it with a
`foreign_key_check` afterwards.

**A test that models the fix instead of the thing.** The rebuild test shipped in
#126 built a toy two-table schema with no `RESTRICT` child. It proved the
technique and nothing about the migration. A migration test starts from a
populated catalogue at the previous schema version, or it proves nothing.

**Writing the right value in the documentation and deriving another in the
code.** This happened four times. The last one cost a failed release: the README
and the Compose file both said `ghcr.io/instazdll/…`, and the workflow was built
from `${{ github.repository }}`, which keeps the owner's casing. Before claiming
a behaviour exists, read it in the code or write the test that fails without it.

**Review counts do not trend.** Successive passes returned 14, 9, 10, 1, 1, then
10 findings — the last pass, on the final commit, found the most serious one of
the series. A falling count is not evidence of a settling surface.

## House rules that are not negotiable

Every code change goes through a branch and a reviewed pull request; only
documentation may go straight to `main`, and that authorization is asked for each
time. Commits are signed off (`git commit -s`) and follow Conventional Commits.
Migrations are immutable once merged. Audio files are never written. No tag or
release is created without an explicit request from the operator.
