# WaveFlow Server 2.1.1

A security release. One audio file with a crafted tag could crash the server, and keep crashing it on every restart. Every version from 2.0.0 to 2.1.0 is affected, the image and the standalone archives alike. Nothing else changes, so upgrade as soon as you can.

## Security

- **A file whose ID3v2 chapter frames nest no longer crashes the server.** A chapter frame (`CHAP` or `CTOC`) can hold frames of its own, and the tag readers recursed once per nested level, without limit. A tag of a few kilobytes was enough to overflow the stack, which aborts the whole process and cannot be caught from inside it.

  The file could arrive in two ways. An account allowed to upload to a library could send it: the server put it in the library, then crashed reading it. Or it could be placed in a scanned folder, where the next scan read it. Either way the file stayed in the library, so the scan at start-up met it again and the server crashed on every restart, until someone found the file and removed it by hand.

  The server now measures how deep a tag's chapter frames nest before reading it, in every format, and in the ID3 tag a DSF or DFF file carries. One chapter frame inside another is not refused: the limit is three levels under the first, well short of the depth that overflows the stack, and nothing real nests them at all. Past that limit:

  - an upload of the file is refused with `422`, and nothing is left in the library;
  - a scan records an error for the file and goes on with the rest;
  - the server stays up, and starts normally.

  A real chapter layout, with a table of contents, titled chapters, links and pictures, is read as before. The check refuses rather than risks a crash, so a file that repeats the names `CHAP` or `CTOC` several times in a place a reader does not always read to its end can be refused too. No real file is known to.

  Only availability was affected: the server went down, and nothing was read or changed that should not have been. The fix is [#426](https://github.com/InstaZDLL/waveflow-server/pull/426).

## If you cannot upgrade yet

- Turn uploads off on every library, or leave upload rights only with people you trust.
- If your server already crashes at every start, remove the file from the library folder. It is usually the audio file uploaded or added last.

## Install

```bash
docker run -d --name waveflow \
  -p 4533:4533 \
  -v waveflow-data:/data \
  -v /path/to/music:/music:ro \
  ghcr.io/instazdll/waveflow-server:2.1.1
```

The image runs on `linux/amd64` and `linux/arm64`, and is the same, digest for digest, on Docker Hub as `instazdll/waveflow-server:2.1.1`. `latest` now follows this release. The standalone archives for Windows, macOS and Linux are attached below, with `SHA256SUMS` over all of them.

## Upgrading from 2.1.0

Pull `2.1.1` and start it on the same data volume. With an archive, use the new folder in place of the old one, carrying over what you changed in `laptop.env`: your data is kept apart from that folder. The database schema has not changed, so there is nothing to migrate, and `2.1.0` still opens the same data should you need to go back.

A server that crashed on such a file needs nothing more than the upgrade: `2.1.1` starts, its scan records an error for the file, and the file stays where it is until you remove it.

Coming from 2.0.1 or earlier, read the [2.1.0 notes](https://github.com/InstaZDLL/waveflow-server/blob/v2.1.1/docs/releases/v2.1.0.md#upgrading-from-201) first: that upgrade changes the schema and measures every lossless file again.
